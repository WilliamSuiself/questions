# 三国问答小程序 · 题目数据结构设计

> 目标：所有题干、选项、答案、解析都以罗贯中《三国演义》一百二十回原文为唯一依据；
> 评书、戏曲、民间演绎（《三国演义》之外的三国故事）不作为正确答案来源。

## 一、整体设计取舍

题库文件是**纯数据**，不带任何业务逻辑。小程序端只负责加载、出题、判分、统计。
这样做的收益：

- 题库可以被小程序、公众号 H5、后台管理端、离线题库 App 共用，一份数据多处用；
- 题目增删只动 JSON，不用发版；
- 校验脚本（`scripts/validate.mjs`）可以在每次提交前自动把关，把「答案越界」「选项重复」「解析缺失」这类低级错误挡在 CI 里。

### 关键取舍：选项用 map，答案存 key

```json
"options": {
  "A": "玄德",
  "B": "孟德",
  "C": "仲谋",
  "D": "伯约"
},
"answer": "A"
```

**不用** `options: ["玄德", "孟德", ...]` + `answer: 0` 的写法。原因：

1. 小程序端 `wx:for="{{item.options}}"` 直接遍历对象即可，键名 `A/B/C/D` 天然就是选项序号，不用另外维护一个 `label` 字段；
2. **打乱选项顺序后，答案索引极易漏改**——这是选择题类小程序最常见的线上事故：用数组存答案时，只要排序函数改了顺序而没同步改 `answer`，整道题就会判错。存 key 则不存在这个问题，`answer` 永远是 `"A"` 这种语义标识；
3. 答案 key 与解析文本里「A 是…、B 是…」的说明天然对齐，写解析时不会错位。

## 二、字段定义

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 是 | `sg-001` ~ `sg-302`，错题本、收藏、答题记录的主键 |
| `type` | string | 是 | 目前只有 `single`（单选），预留 `multi`（多选）、`judge`（判断） |
| `stem` | string | 是 | 题干。必须是一个完整问句、只问一个考点，长度 6~120 |
| `options` | object | 是 | 恰好 `A/B/C/D` 四个键，值为选项文本 |
| `answer` | string | 是 | 正确答案的**键名**（`"A"`），必须存在于 `options` 中 |
| `analysis` | string | 是 | 解析。必须给出原文依据，并点明干扰项错在哪 |
| `difficulty` | int | 是 | `1` 入门（字号、地名等记忆型）/ `2` 中等（情节因果型）/ `3` 难（细节、诗词原句、人名混淆型） |
| `category` | string | 是 | 九个大类之一，见下表 |
| `tags` | string[] | 是 | 1~5 个细粒度标签，用于检索和专项练习 |
| `source.chapter` | int \| null | 是 | 原著回目号 1~120；跨回情节或存疑时填 `null` |
| `source.scene` | string | 是 | 情节名，如「三顾茅庐」「舌战群儒」 |
| `source.evidence` | string | 是 | **原文依据**：原著原句或原著情节的忠实梗概 |

### `source` 三件套是「忠于原文」的可核查凭证

只有 `evidence` 是真正有约束力的字段：

- `chapter` 是导航用的，回目号错了不影响题目本身的正确性，所以允许 `null` 而不是硬填一个错号；
- `scene` 让人一眼看出这题考的是哪个情节；
- `evidence` 是**判卷依据**：写题时如果某句话在原著里找不到出处，就说明这题要么写错了、要么是民间演绎，必须删掉或改写。

例子（`sg-021`）：

```json
"source": {
  "chapter": 1,
  "scene": "桃园结义·祭告天地",
  "evidence": "不求同年同月同日生，只愿同年同月同日死。"
}
```

### `evidence` 的写法与核验

`evidence` 采用**原著原句的简体转写**（「瑯琊」这类异体字保留原字形，其余转简体）。

每条 evidence 都必须能回查原著，由 `scripts/verify-against-text.py` 自动核验：
脚本抓取维基文库《三国演义》一百二十回全文并转简体，逐题比对 `evidence` 是否真的出自所标的 `source.chapter`——

- **原句精确命中**：evidence 是该回原文的连续片段；
- **梗概型**：evidence 是该回情节的忠实转述（关键词级命中）；
- **依据存疑**：查不到 → 脚本 exit 1，这条题的依据不成立，必须改。

当前 302 题的结果：285 条原句精确命中、17 条梗概型、0 条存疑。

校对过程中被脚本抓出来的典型问题（都已修正）：

- 把《三国志》的措辞当成《三国演义》原文 —— 「跨有荆益」「奉天子以令不臣」原著均无，前者原著作「若跨有荆、益，保其岩阻」，后者在第十四回是「今天子蒙尘，将军诚因此时首倡义兵，奉天子以从众望」；
- 把评书 / 后世俗说当成原著 —— 「食之无肉，弃之有味」（原著第七十二回杨修原话是「食之无肉，弃之有味」，反过来常见）、「羽扇纶巾」原著并无此四字连用；
- 曹操的《观沧海》《龟虽寿》《蒿里行》**原著正文并不收录**，不能拿曹操文集当原著 —— 这三题已换成原著里真实存在的《铜雀台赋》、卧龙庄门联、第五十七回「后人有诗」；
- 「马谡献计降姜维」是评书与民间演义的说法，原著第九十三回并无马谡其人；
- 原著正文第 41 回说曹昂是曹操**妾室刘氏**所生，与史传不同 —— 这正是「忠于原著」要留意的地方，已单独成题。

### 第二轮扩充到 300 题时新抓出来的问题

跨过 100 题之后，题库规模一大，原来只在首 100 题里靠人工过目的毛病就浮出来了，
新增的三个脚本（`check-batch.py` / `check-similarity.py` / 全库干扰项逐字比对）各抓到一批：

- **诗的归属张冠李戴**：第六十七回「后人有诗叹曰：妨贤卖主逞奇功，积得金银总是空」是叹杨松卖主求荣被杀，
  原先却写成「评张辽威震逍遥津」，解析也跟着编了一段「以郭嘉、荀攸两次反对讨蜀提醒读者」——
  这段解读原著里根本没有。已改回杨松，并把本回另一首真正咏叹刘备、孙权胜负的诗拿来当干扰项。
- **干扰项也是原著原句**：第七十二回杨修解「鸡肋」的原话是「食之无肉，弃之有味。今进不能胜，退恐人笑」，
  原先的干扰项「鸡肋者，进不能胜，退恐人笑」等于把原著后半句截出来当错项，等于给了两个正确答案。
  已改成只差一字的「弃之无味」，逼玩家看清原著到底是「有味」还是「无味」。
- **干扰项与题干同义，导致双解**：辛宪英那段，干扰项「曹将军非司马公之对手，必然败矣」本身就是辛宪英对弟弟说的话，
  题干若只问「她对弟弟说的是哪一句」，就有两个正确答案。已把题干收紧到「判断司马懿用意时」，
  并把该干扰项改掉一字，使其不再逐字命中原著。
- **曹操文集里的诗必须锚定回目**：《短歌行》虽被第四十八回曹操横槊赋诗时整首收录，
  但它同时也是曹操文集里的作品，题干必须写明「《三国演义》第四十八回」，
  否则读者无从判断考的是原著正文还是曹操文集。这与「《观沧海》《龟虽寿》《蒿里行》原著并不收录」是同一条纪律的两面。

### 答案位置分布

`answer` 存的是**键名**而不是数组下标，所以打乱选项顺序不会让答案错位；
但数据本身也必须没有位置规律 —— 否则一旦某处没做打乱（练习模式、导出卷面、第三方对接），
玩家就能靠「选 A」拿分。

第一版 100 题的 `answer` 全部落在 `A`，扩到 300 题后 `A` 高达 188 题。
`scripts/archive/rebalance-answers.py` 做了重排：**只改「哪个字母装正确答案」和「选项文本落到哪个字母」，
选项文本本身一个字都不改**，题干、解析、来源、难度、分类全部保持原样；
解析里少数引用了「B 出自……」的字母按文本内容反查新字母同步改写。
重排后 300 题的答案位置为 A / B / C / D **各 75 题**（补完第 6、99 回两题后为 75 / 76 / 75 / 76）。

### 分类体系

| category | 含义 | 题量（累计 302 题） |
|---|---|---|
| `人物字号` | 表字、别号、籍贯的机械记忆 | 37 |
| `人物生平` | 身世、评价、封号、关键转折 | 30 |
| `经典场景` | 名场面细节（桃园、煮酒、三顾、华容道…） | 60 |
| `谋略计策` | 三十六计类：连环、苦肉、反间、空城… | 38 |
| `经典战役` | 战役经过与关键人物 | 45 |
| `诗词原文` | 原著中的诗、赋、令、表文原句 | 23 |
| `兵器坐骑` | 兵器、坐骑、宝物 | 16 |
| `地名官职` | 都城、州郡、官爵 | 22 |
| `成语典故` | 成语的原著出处 | 31 |

分类不是给玩家看的标签系统，也是**出题策略的输入**：一场 10 题的快速局可以按 `difficulty` 抽，一轮专题可以按 `category` 抽。

## 三、题型扩展预留

`type` 目前恒为 `single`。将来要加多选题，只需：

```json
{
  "id": "sg-101",
  "type": "multi",
  "stem": "以下哪些是《三国演义》中「桃园结义」三人？",
  "options": { "A": "刘备", "B": "关羽", "C": "张飞", "D": "赵云" },
  "answer": ["A", "B", "C"],
  ...
}
```

对应的 schema 需要把 `answer` 改成 `oneOf: [string, string[]]`，小程序端判分逻辑按 `type` 分支即可。**在真正需要之前不要提前实现**——多选题的解析文案、错题本的展示逻辑都要跟着变。

## 四、线上部署的防作弊处理

`questions.json` 里同时含答案和解析。如果整包塞进小程序代码包，用小程序反编译工具可以直接看到答案。

建议拆成两份（`scripts/split-public.mjs` 已实现）：

- `questions.public.json` —— 题面 + 选项 + 分类 + 难度，**不含** `answer` / `analysis`，随包发布；
- `questions.answers.json` —— 答案 + 解析 + 原文依据，答题结束后由云函数下发，或用简单的服务端加密。

判分在服务端做，前端只负责提交作答。这样即使包被拆，题库里也没有答案。

## 五、数据文件清单

```
data/
├── questions.json                  # 主题库（302 题，含答案解析）
├── questions.public.json           # 线上面包（拆掉答案解析）
├── questions.answers.json          # 答案包（服务端下发）
├── questions.meta.json             # 元信息 + 分类/难度分布
├── schema/question.schema.json     # JSON Schema (draft-07)
└── _batches/                       # 分批编辑源文件，合并脚本的输入
```

`_batches/` 是**编辑源**，`questions.json` 是**构建产物**。加题时在 `_batches/` 里新建 `batch-11.json`（或追加到现有批次），然后跑 `npm run build` 重新合并 —— 合并时会按顺序重新编号 `sg-001`…`sg-302`，所以批次内部的 id 写什么都无所谓，但**批次文件的先后顺序决定最终题号**。
